# M0 真实页面验证记录（脱敏）

日期：2026-10-24。环境：Windows 浏览器，抖音网页版，用户本人已登录。本文只记录结构数据和 UI 行为，不包含任何私信正文或可识别个人信息。

## 已确认

- 页面有 1 个可编辑区域，2 个带纵向滚动条的区域。
- 左侧会话列表宽约 303 px；右侧聊天区域自 x≈304 px 开始，与输入框对齐。
- 聊天容器下只有一个直接列表子容器。其直接子项为带 `data-index` 属性的 `div`。
- 第一次采样：渲染 23 个索引，范围 `0..22`，整个聊天区约 490 个后代元素。
- 用户向上滚动到**更早日期**后的第二次采样：渲染 29 个索引，范围 `262..290`，约 595 个后代元素。
- 这两个快照之间的索引未被采样，不能把它们判为服务端缺失消息；需要持续监听滚动期间的节点增删。
- 网页自带右键「转成文字」；转换成功后，文字显示在原语音消息**下方**。
- 不同消息样本的 DOM 组成有差异（`div`、`p`、`span`、`img`、`canvas`），需要类型适配。

## 技术推断与待验证

- **推断：** `data-index` 很可能是虚拟列表项的位置而不是稳定消息 ID。需要通过持续观察验证是否重编号、是否连续；不能用它取代平台消息 ID。
- **待验证：** MutationObserver 加周期轮询能否捕获慢速上翻时全部暂时渲染的索引。
- **待验证：** 原生语音转写右键菜单能否以扩展内容脚本可靠触发，并稳定找到对应转写文字。
- **待验证：** 历史终止边界的 DOM/API 证据，以及完整消息解析器。

## 验证工具

- M0.4 `index-monitor.js`：用户手动上翻时记录经过的 `data-index` 数字，停止后生成报告。它**不读取或导出聊天内容**，不能当作全量备份。
- 真正采集器应在新消息 DOM 节点出现时立即持久化，离开屏幕后也不会丢失；只有证实最旧可访问历史边界并完成语音转写，才允许显示相应完成状态。

## M0.4 连续滚动通过（2026-10-24，用户提供的脱敏报告）

- 监听时长：约 26 秒，列表 `scrollTop` 从 `0` 变化到 `40835`。
- 观察到的索引：`0..762`，共 **763** 个；这一范围内未观察索引 **0** 个。
- 这证明在这次手动滚动速度下，DOM 监听没有漏掉中间的列表位置；此前“只存在 20–30 个 DOM 项”的虚拟列表限制可以通过滚动时逐批暂存解决。
- **尚不能推断：** 763 个是完整历史消息数、最旧边界已到达、每个位置恰好对应一条真实消息、语音已转写。索引不是平台稳定消息 ID。

## M1.0 原始内容采集测试（0.1.5，用户提供的脱敏汇总）

- 已暂存 968 个虚拟列表项，索引 `0..967`，未观察索引 0 个。
- 无可见文字 62 个；这可能是图片、语音等非文本项，不能直接认定为遗漏。
- 155 个疑似文本冲突（约 16.0%）；读取异常 0 个。**该冲突率不能直接解释为消息错位率**：0.1.5 同时读取了内部索引和可能已被移除的 DOM 节点，而且使用“较长文本优先”的启发式策略，有误配风险。
- M1.1 / 0.1.6 改为仅采集实时直接列表项，要求可见文字稳定至少 180ms 后优先选取，区分瞬时变化与已稳定文本的实质冲突，并标记尚未稳定的条目。继续维持 `partial`。

## M1.1 用户正文核对结果与顺序规则

- 用户再次人工核对 0.1.6：**不再出现正文串到别的消息、重复或错位**（小样本人工验证；不代表全量消息/附件完整）。
- 唯一指出的问题是导出顺序反了：**索引小的位于较近日期，索引大的位于更早日期**。0.1.6 采用升序，导致 TXT 上面是最近消息，下面是过去消息。
